## How to execute
- The **Gate** is a technical dependency, NOT a compulsory day-by-day schedule. Work critical path continuously.
- Execute top unblocked task; do not randomly jump to visual polish while core pipeline unproven. But get the hero UI visible early, as a tangible integration target.
- Each task is done only with runnable code, focused tests, and evidence in `PROGRESS.md`. Keep status honest.
- No Azure provisioning without owner consent. SDK code and offline tests are allowed.
- Don't generate placeholder components for all tasks; implement in complete tested increments.
- Each task should have a precise `FILES`, `TESTS`, `DEMO`, and `BLOCKERS` entry in progress log.

## Gate acceptance (end-to-end outcomes, no fixed daily schedule)

- **Gate A:** A new event affects score/state; repeated-channel candidate emerges solely from evidence. Fully offline testable.
- **Gate B:** Candidate sent through live Foundry-backed distinct agents, checked, cached, rendered; trace available. No fake results.
- **Gate C:** Hero experience is premium, stable and the vertical slice is demonstrable to a stranger.
- **Gate D:** Complex football law decisions, change of score and tactical detectors genuinely function in simulations.
- **Gate E:** One event is meaningfully different in Commentator, Studio and Fan. It is NOT just three cards with identical text.
- **Gate F:** Public working judging endpoint + repo + video + submission. No unapproved spending.

**Important:** Gate B must be pursued early enough to discover Foundry account issues, in parallel with local Gate A work only where dependencies allow. No hero work is considered DONE if the backend is a scripted fixture explanation instead of computed insight.
